# Universal Directives

These directives apply to **all content** (code, prose, config, docs) in any project.

| § | Principle | Summary |
| ---- | ---- | ---- |
| §1 | **No Backward Compatibility** | Refactor freely in internal codebases. Git is the only archive. No compatibility shims, `_old` suffixes, or deprecated accommodations. SemVer only for published libraries with external consumers. |
| §2 | **YAGNI** | No speculative abstractions, helper utilities, or wrappers for one-time operations. No premature generalization; three similar lines beat an unnecessary abstraction. Delete dead code; do not comment it out. |
| §3 | **Explicit Configuration** | Config values declared in files or models, passed as objects, extracted at leaf nodes. Never instantiate global config. No hidden defaults in code. Missing required config fails at startup. |
| §4 | **Strict Typing** | Precise types over pass-through containers. Deserialize to concrete structs at boundaries. No `Any`, `serde_json::Value`, or raw `HashMap` in domain logic. Preserve typed models through internal logic; serialize only at output boundaries. |
| §5 | **Required means Required** | No `Optional[T]` / `Option<T>` / `None` default for parameters that are logically required. A required parameter with a None default is a lie the type system cannot catch. Tests adapt to required interfaces; do not weaken production to simplify testing. |
| §6 | **Fail Fast** | Bubble errors. Use specific exception types with actionable context. Missing config, invalid patterns, unresolvable paths: fail at startup, not at first use. Validate once at boundaries; trust types internally. |
| §7 | **Composition Over Implicit Context** | No global state, no implicit thread-local state, no module-level singletons reached for at call sites. Dependencies flow through explicit composition — passed as parameters or threaded through a context object — never via ambient or hidden state the caller cannot see. The specific shape of that context object is governed by §14. |
| §8 | **EAFP Over LBYL** | Trust validated data. No redundant `hasattr`/`if let Some`/`if key in dict` on types the system already guarantees. Defensive checks only at system boundaries (external data, user input, I/O). |
| §9 | **Batch-First APIs** | Functions should accept iterables/slices by default. Singleton wrappers only when necessary. Reduces per-call overhead and enables internal optimization. |
| §10 | **Logging** | All diagnostics to logging, never ad-hoc console writes. Name loggers by class or module. Acquire and configure handlers once, at startup (§14). A failure is logged once, at the frame that handles it (§6). Never log credentials, secrets, or personal data. |
| §11 | **Production Code Primacy** | Production code has right-of-way. Tests adapt to production, never the reverse. Never weaken production types, structure, or interfaces to satisfy tests — but widening a genuine, independently-valuable configuration surface (§16 valve) is production-improving, not weakening. |
| §12 | **Testing** | Separate unit (fast, isolated) from integration (multi-component; §16 mandates a cross-boundary end-to-end pass within the integration tier). Coverage discipline per project. Tests in dedicated locations, not inlined in production files. |
| §13 | **Configuration Closure** | Every deserialized configuration field must reach a non-test consumer. The configuration→consumer graph is closed in both directions: §6 enforces the reverse edge (missing required config → startup error); §13 enforces the forward edge (orphan config → CI error). Each config struct gets a paired integration test asserting consumption; CI rejects unread keys. |
| §14 | **Configuration Discipline** | Use the `AppConfig` + `AppContext` construction pattern. `AppConfig` holds static external values (config files, env vars, CLI params); `AppContext` holds `AppConfig` plus the app-wide resources derived from it (DB pools, API clients, queues, singleton services); they are both constructed once at startup, and passed as the single source of truth for the application's lifetime. Never reconstruct a resource that already exists in context. Pass `AppConfig`/`AppContext` through intermediate frames as a unit; unpack individual values only in the leaf nodes that consume them — keeps leaf signatures narrowly typed against just what they use while avoiding parameter bloat in deep call trees. |
| §15 | **Test Via Production Path** | Tests exercise production code paths and production-shape data — no parallel, lower-fidelity backdoor. Construct application state (config, context, resources) only through the production pipeline the application itself uses, and consume it the way production does. No in-test literal construction of config objects; no test-only constructors or visibility-widening flags on production types; no production enum variants, constructors, or trait impls that exist solely for tests; no synthetic in-memory substitutes for production-shape data; no minting resources directly when a context already provides them. Fixtures are production artifacts loaded by production loaders, every required field populated to deterministic real values. When a test cannot route through a production path, drop it (§11 primacy) — but for a boundary-crossing test (§16) apply the §16 configurability valve before concluding it cannot route; extend production only when a real production configuration is demonstrably and wrongly rejected — a concrete trigger, never hypothetical. |
| §16 | **E2E ASAP** | Every pipeline that crosses a boundary (a crate, store, process, vendor, or serialization boundary) has a breadth-first end-to-end test that drives one real row through the whole pipe, exercising the linkage (FK, id-namespace, contract/enum, serialization, schema drift) that within-module unit tests structurally cannot reach. The single-real-row floor is sufficient — presence-early outranks coverage-late. Introduced early (first-wiring / per-phase gate), run routinely (CI / boot smoke), never deferred to project end. A valve exposes only valid production-reachable states; an invalid state (e.g. an FK violation) is tested via the production rejection/failure path, and if no valid production-reachable cross-boundary state exists the pipeline claim is false, not a §13 conflict. |
| §17 | **Sets by Reference** | Where a set's membership is assayable from its source of truth — files on disk, table rows, defined provisions — refer to it by name or defining property, never by restated count, range, or enumeration. Naming member subsets to attach facts to them is content; the goal is to avoid list rot and token waste. |
